# Code Review — Task 2 (v1.4.3): M4A 写入分派 + tagSize M4A 估算

Reviewed files: `src/tags.ts` (`isM4aBytes`, `toMp4TagSet`, `embedTagsIntoBytes`, `writeAudioTags`), `src/tagSize.ts` (`M4A_FIXED_OVERHEAD`, `m4aTextAtomBytes`, `m4aCoverAtomBytes`, `estimateM4aEmbeddedSize`), `tests/tag-size.test.ts` (3 new cases). Spec §2.2 passed already.

## Strengths

- **Byte-based dispatch is the right call.** `writeAudioTags`/`embedTagsIntoBytes` deciding on container bytes (not extension) matches the project's own `detectAudioContainer` "伪扩展名" philosophy — an `.mp3` file that's really M4A gets the correct writer and is not corrupted. Good consistency with the plan's intent.
- **Failure-path audit is clean.** `writeAudioTags` restores the original on every path *after* a write has occurred: write-fail (line 274), verify-fail lengthOk/readable (line 281), and catch (line 286). The `!updated` early return (line 272) correctly needs no restore because nothing was written. Backup `original` is captured correctly at line 269.
- **`toMp4TagSet` is semantically correct** for the `Mp4TagSet` contract: `undefined` cover → `undefined` (keep), `null` cover → `null` (remove), object → `.data`.
- **Per-file responsibility preserved.** `tagSize.ts` stays dependency-free pure logic (no obsidian/resize/format imports added); the M4A estimator follows the existing `SizeTags` shape. No file bloat — tags.ts grew only ~35 lines for the new dispatch.
- **Comments only at complex logic**; Chinese comments consistent with the file. No new `any` (strict-safe).

## Issues

### Important

**1. Triple duplication of the M4A magic check — unify on one detector.**
`isM4aBytes` (`src/tags.ts:34-36`, `b.length >= 12 && bytes[4..7]=='ftyp'`) is functionally the same check as `looksLikeM4a` (`src/downloadManager.ts:896-898`, `>= 8`) and the inline branch in `detectAudioContainer` (`src/songScanner.ts:49`, `>= 8`). Three copies of one detector, with slightly different length thresholds (12 vs 8), so they can already diverge on a malformed 8–11 byte header. This file also keeps its own copy while Task 3's modal uses the separate `detectAudioContainer` on the *same* bytes — two independent containers opinions at edit time.
**Fix:** reuse one canonical detector. Prefer `detectAudioContainer` in `songScanner.ts` — `writeAudioTags` and `embedTagsIntoBytes` only need `=== 'm4a'`; drop `isM4aBytes` and `looksLikeM4a` in favor of it. (If you must keep a micro helper for hot paths, centralize it in one module and have `songScanner`/`downloadManager`/`tags` all import it.)

**2. `writeAudioTags` dispatch is blunt: any non-m4a goes to node-id3, including FLAC/OGG/corrupt.**
`src/tags.ts:268` — `if (!isM4aBytes(buf)) return writeMp3Tags(...)`. A `.mp3` extension frame that is actually FLAC or OGG (or truncated/`unknown` bytes) would run `NodeID3.update`, writing ID3v2 frames into a non-MP3 container and corrupting it. The only guard today lives in the *caller* (`TagEditorModal` refuse-stream) and in `songScanner.detectAudioContainer`, so `writeAudioTags` is safe only because of an external gate nothing about its signature advertises.
**Fix:** make the dispatch defensive at the boundary, consistent with the plan's own "避免损坏文件" intent — distinguish `'unknown'`/`'flac'`/`'ogg'` and fail/restore rather than treating them as mp3. At minimum add a doc comment on the contract ("caller MUST gate to mp3/m4a") and rely on one detector (see #1), not two.

### Minor

**3. `writeAudioTags` double-reads the file on the mp3 path.** It reads the full buffer at line 266 only to discard it and let `writeMp3Tags` (`src/tags.ts:229`) read it again. For non-m4a files the whole file is read twice.
**Fix:** either have `writeAudioTags` pass the already-read `buf` into an internal variant of `writeMp3Tags`, or delegate up-front before reading (dispatch always needs the first 12 bytes though). Low impact, but the read is avoidable.

**4. `M4A_FIXED_OVERHEAD = 40` doesn't reconcile with its own comment.**
`src/tagSize.ts:55-56` — comment claims "moov/udta/meta/ilst 4 层 box 头 + meta version/flags" = 4×8 + 4 = **36**, not 40. The extra 4 is unexplained (maybe intent includes the hdlr or an off-by-one). Harmless for the relative delta (baseline & live use the same function so the constant cancels), but the constant's derivation is unverifiable.
**Fix:** align the comment with the math (e.g. "…+ version/flags 4 + reserved 4" if that's the intent), or add one frozen comment showing the breakdown so a future edit of `writeMp4Tags` can reconcile it.

**5. Test asserts re-derive the same closed form instead of an independent ground truth.**
`tests/tag-size.test.ts:9,14,18` — `expect(size).toBe(40 + 19 + 17 + 17 + 22)` recomputes `M4A_FIXED_OVERHEAD + Σ(16 + utf8Len)` literally, so a wrong constant is faithfully echoed. For a pure size estimator this pins the constants (acceptable), but the M4A overhead/atom-header values here are asserted against themselves rather than a spec citation.
**Fix:** add a short comment tying each term to `8 + 8` atom offset boxes and cite the `M4A_FIXED_OVERHEAD` breakdown (see #4), so the test doubles as documentation.

## Assessment

**Needs fixes.** Two issues block approval:

- **Important #1** — unify the duplicated M4A magic detection onto one canonical detector (`isM4aBytes`/`looksLikeM4a`/`detectAudioContainer` share the same logic with drifting thresholds; also the modal and `writeAudioTags` currently use different detectors on the same bytes).
- **Important #2** — `writeAudioTags` (and `embedTagsIntoBytes`) dispatch *all* non-m4a to node-id3, so a FLAC/OGG/`unknown` file that reaches it via the caller's extension gate would be corrupted; the boundary must guard or clearly delegate to a single detector.

Minor #3–#5 are recommended cleanups that do not block.
